# CHANGELOG-748 — à fusionner dans CHANGELOG.md

## 11 octobre 2026 — issue #748

Interruption d'une issue : retour visuel immédiat, protection contre le double envoi, et prise en compte des processus zombies (verrou périmé) — incident Scrabble #452.

- **`watcher.py` — `_pid_vivant` détecte désormais les zombies sous Linux** : `os.kill(pid, 0)` réussit pour un process ZOMBIE (entrée encore présente dans la table des process tant que le parent ne l'a pas réapé) — exactement le cas vécu sur Scrabble #452 (watcher tué devenu zombie, verrou jamais nettoyé). Nouvelle fonction `_etat_processus_linux(pid)` lit le 3ᵉ champ de `/proc/<pid>/stat` ; `_pid_vivant` renvoie `False` si l'état est `'Z'`, un fait certain au même titre qu'un PID introuvable (asymétrie documentée de la fonction préservée). Repli sur le comportement antérieur (prudence, `True`) si `/proc` est absent ou la lecture échoue — rien ne change sous Windows. La tentative de récupération `waitpid` (`_reaper_best_effort`, `app/interruption.py`) est conservée telle quelle.
- **`app/interruption.py` — protection serveur contre le double appel** : avant cette issue, `route_interrompre()` n'avait AUCUNE garde — deux appels rapprochés pour le MÊME projet (interrompre_linux/interrompre_windows ciblent l'arbre entier du watcher d'un projet, pas une issue précise) exécutaient chacun entièrement label + étapes + commentaire GitHub, en double (vérifié par lecture de code et par test). Un verrou en mémoire (`threading.Lock` + `set` de projets, `_projets_en_interruption`) court-circuite désormais un second appel concurrent pour le même projet : réponse immédiate HTTP 409 (`deja_en_cours: true`), aucune étape exécutée. Cœur technique factorisé dans `_executer_interruption()` (appelable directement sans la garde, utilisé par les tests pour documenter le comportement antérieur).
- **`static/js/actions_ligne.js` / `static/js/app.js` — retour visuel + garde JS** : dès la confirmation acceptée, les deux déclencheurs existants (icône ✓/✕ de la ligne, bouton « Interrompre et relancer » du panneau latéral) sont désactivés visuellement (`_marquerInterruptionEnCours`, curseur d'attente, libellé « Interruption en cours… » sur le bouton) jusqu'à la réponse du serveur ; réactivés + erreur affichée comme avant en cas d'échec ; fenêtre de résultat inchangée en cas de succès. Garde par couple (projet, numéro) partagée par les deux déclencheurs (logique pure `cleInterruption`/`demarrerInterruption`/`terminerInterruption`, exposée via `window.Bridge.actionsLigne`) : un clic pendant qu'une interruption est déjà en cours pour ce couple est ignoré avec un message court. `static/css/resultats.css` : styles `.badge-interrompre-attente` (icône) et `.en-attente-interruption` (bouton panneau).
- **Panneau Infrastructure** : un verrou orphelin (process mort OU zombie) n'est plus compté « en cours » par `watcher.taches_en_cours` (bénéficie automatiquement de la correction `_pid_vivant` ci-dessus, aucun changement de code nécessaire dans cette fonction) — jamais supprimé silencieusement, ni si le process est réellement vivant, ni par cette fonction elle-même (pas son rôle). Le point vert/dot du panneau (`app/watchers.py::watcher_actif`) bénéficie de la même correction. Le texte « N en cours, N en file » (`resumeProjetMonitoring`, `static/js/app.js`) reste basé sur les labels GitHub, pas sur les verrous — non affecté, déjà correct une fois la liste rechargée.
- **Tests** : `tests/test_pid_vivant_zombie_748.py` (zombie réel non réapé → `False` ; process vivant → `True` ; PID inexistant → `False`, non-régression #584 ; repli silencieux si `/proc` illisible). `tests/test_interruption_zombie_748.py` (watcher zombie dont le vrai parent n'est PAS le process de test, reproduisant la limite documentée de `_reaper_best_effort` : l'attente conclut « arbre mort » en moins d'une seconde au lieu d'épuiser les 5s, verrous principal + worktree supprimés, plus aucune tâche en cours pour `taches_en_cours` ; verrou orphelin mort+dossier absent ignoré sans être supprimé). `tests/test_interruption_double_appel_748.py` (documente le comportement SANS garde — deux appels concurrents dupliquent tout — puis vérifie qu'AVEC `route_interrompre`, un second appel concurrent répond 409 sans rien refaire). `static/js/tests/actions_ligne.test.js` : nouveaux cas pour `cleInterruption`/`demarrerInterruption`/`terminerInterruption` (acceptation/refus par couple, libération, no-op sur couple absent). Les 61 fichiers de `tests/test_*.py` (`tests/lancer_tous_les_tests.py`) et les 288 tests JS (`node --test static/js/socle/tests/ static/js/tests/`) passent.
- **Documentation** : `ARCHITECTURE.md` — nouvelle section §11 « Interruption d'une issue et verrous de traitement » (verrous fichier, `_pid_vivant`/zombies, flux serveur `/interrompre` et sa garde, retour visuel + garde JS). `BRIDGE_AGENT_DOC.md` non touché (hors périmètre de l'issue).
