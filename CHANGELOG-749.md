# CHANGELOG-749 — à fusionner dans CHANGELOG.md

## 11 octobre 2026 — issue #749

Worktrees `mode_write` sous CCW (Windows) : création désormais dans un dossier dédié `worktrees`, symétrique du dossier dédié CCL (issue #740), au lieu du répertoire frère historique où ils se mélangeaient aux clones de projets (`C:\CCW\Rummikub`, `C:\CCW\Scrabble`, ...).

- **`watcher.py` — `_chemin_worktree`** : la sélection du dossier dédié dépend désormais de `os.name`, sur les deux branches. Sous **CCL (Linux)**, aucun changement : `DOSSIER_WORKTREES_DEDIE` (constante fixe, par défaut `~/worktrees`). Sous **CCW (Windows)**, nouvelle fonction `_dossier_worktrees_dedie_windows()` qui recalcule `CFG.rep_travail.parent / "worktrees"` à CHAQUE appel (ex. `C:\CCW\worktrees` pour un projet dont `REP_TRAVAIL` est `C:\CCW\Scrabble`) — **jamais** à partir du profil utilisateur (`Path.home()`/`%USERPROFILE%`) : les services CCW tournent sous NSSM, éventuellement sous un compte distinct de l'utilisateur interactif, dont le profil n'a aucun rapport avec l'installation. Le mécanisme de création/repli (créé au besoin via `mkdir`, repli sur l'ancien emplacement frère de `REP_TRAVAIL` + `log.warning` explicite si le dossier dédié ne peut pas être créé ou n'est pas accessible en écriture) est désormais partagé entre les deux plateformes (auparavant spécifique à CCL). Nom et suffixes (`-bis`/`-ter`, issue #611) inchangés. Nouvelle constante `NOM_DOSSIER_WORKTREES_DEDIE = "worktrees"`, partagée par les deux calculs.
- **Aucune migration** : les worktrees déjà créés à l'ancien emplacement (frère du projet, sur les deux plateformes) ne sont pas déplacés — `_trouver_worktree_reutilisable` les retrouve toujours via `git worktree list` (comparaison par NOM de dossier, jamais par chemin calculé ni par `os.name`), donc une RELANCE (issue #725) continue de les reprendre normalement.
- **`app/interruption.py`** : commentaire de `_lister_worktrees_actifs` mis à jour (mentionnait « CCW... garde cet ancien emplacement sans changement », devenu inexact) — **aucun changement de code** : le mécanisme (interroge `git worktree list`, indépendant de l'emplacement réel) couvrait déjà correctement le nouvel emplacement CCW sans modification.
- **Scripts PowerShell de provisioning** (`interrompre_projet_ccw.ps1`, `nettoyer_verrous_ccw.ps1`, `ccw-commun.psm1`, etc.) : vérifiés par recherche (`grep` sur « worktree »/« issue- ») — aucune dépendance à l'ancien emplacement des worktrees, donc non modifiés, conformément au périmètre de l'issue.
- **Séparateurs de chemin** : les comparaisons existantes (`_lister_worktrees_secondaires`/`_trouver_worktree_reutilisable`, basées sur `Path(...).resolve()`) n'ont nécessité aucune correction — `pathlib.WindowsPath` normalise `/` et `\` de façon identique (démonstration via `PureWindowsPath` dans les nouveaux tests), donc un chemin renvoyé par `git worktree list` (toujours en `/`, même sous Windows) et un chemin calculé nativement (`\`) se résolvent au même objet.
- **Longueur de chemin Windows** : le nouveau chemin ajoute environ dix caractères (`\worktrees`) par rapport à l'ancien emplacement frère — négligeable face à la limite historique de 260 caractères. La configuration `core.longpaths` du poste CCW réel n'a pas pu être vérifiée depuis ce worktree Linux ; voir le rapport de clôture pour la vérification manuelle à faire par Alain.
- **Tests** : nouveau fichier `tests/test_worktree_windows_749.py` — simule `os.name == "nt"` depuis Linux (monkeypatch appliqué APRÈS construction des `Path` nécessaires, pour rester sur de vraies opérations POSIX ; voir le docstring du module pour le détail de cette technique et sa limite : `_trouver_worktree_reutilisable` ne peut pas être exercée sous `os.name="nt"` simulé car elle construit des `Path` nus à partir de `git worktree list`, ce qui lève `NotImplementedError: cannot instantiate 'WindowsPath'` sur une machine non-Windows). Vérifie : dossier dédié dérivé de `REP_TRAVAIL.parent`, jamais de `Path.home()` (piégé) ; création au besoin ; repli + `log.warning` si inaccessible (parent de `REP_TRAVAIL` en lecture seule) ; suffixes `-bis`/`-ter` inchangés ; comportement CCL inchangé avec la même config ; worktree hérité à l'ancien emplacement toujours trouvé par une relance ; comparaison de chemins insensible aux séparateurs (`PureWindowsPath`). Les 62 fichiers `tests/test_*.py` existants (dont `test_worktree_parallelisation_337.py`, `test_reprise_worktree_725.py`, `test_lister_worktrees_actifs_740.py`, ce dernier légèrement retouché en commentaires seulement pour rester exact) passent sans régression.
- **Documentation** : `WORKTREES.md` (§2, « Emplacement ») et `provisioning/windows/REINSTALLATION_CCW.md` (§9, « Repérer et nettoyer les worktrees orphelins ») mis à jour pour décrire l'emplacement CCW. `BRIDGE_AGENT_DOC.md` non touché (hors périmètre de l'issue).

**Vérifications manuelles à faire par Alain sur le poste CCW réel** (non vérifiables depuis ce worktree Linux, cf. rapport de clôture) : exécution réelle de `_chemin_worktree`/`_dossier_worktrees_dedie_windows` sur une vraie installation Windows (création effective de `C:\CCW\worktrees\...`) ; `git config --get core.longpaths` sur `C:\CCW\Bridge_Agent` et sur le `REP_TRAVAIL` de chaque projet dédié ; comportement réel de `_trouver_worktree_reutilisable` avec de vrais chemins Windows (la limite de `pathlib.WindowsPath` empêche de l'exercer depuis Linux).
