# CHANGELOG-752 — à fusionner dans CHANGELOG.md

## 12 octobre 2026 — issue #752

Plancher de 900s pour le TIMEOUT par défaut des issues en écriture dont le fichier déposé n'en précise aucun — plusieurs issues en écriture avaient dépassé leur délai en recevant le défaut `TIMEOUT_CLAUDE` du projet (300s pour 11 projets sur 14), bien trop court pour une tâche d'écriture typique (300-1100s).

- **Constante unique `watcher.PLANCHER_TIMEOUT_ECRITURE` (900s)**, importée par `scripts/watcher_issues_inbox.py` et `app/issues.py` — jamais redéfinie.
- **`scripts/watcher_issues_inbox.py::construire_body`** : le défaut doit être décidé **au dépôt**, seul point où l'absence de `TIMEOUT` reste distinguable d'une valeur voulue (une fois écrit dans l'en-tête de l'issue, les deux cas sont indiscernables). Sans `TIMEOUT` dans le fichier, une issue en écriture reçoit `max(TIMEOUT_CLAUDE, PLANCHER_TIMEOUT_ECRITURE)` ; une tâche Chef en écriture reçoit en plus `max(TIMEOUT_CHEF, PLANCHER_TIMEOUT_ECRITURE)` ; lecture/lecture active restent inchangées. Un `TIMEOUT` présent dans le fichier n'est jamais relevé (seule exception préexistante : le plancher Chef de l'issue #111). La fonction retourne désormais un couple `(body, info_timeout)` ; quand le défaut a dû être calculé, `info_timeout` (ex. « TIMEOUT absent : défaut de 900s appliqué ») est ajouté à la ligne de log du Watcher spool.
- **`watcher.py::extraire_timeout`** — filet de sécurité : nouveau paramètre `mode` (déduit des labels GitHub par l'appelant, jamais du corps) ; si aucune ligne `TIMEOUT` n'est trouvée et que le mode est écriture, le même plancher s'applique — couvre une issue créée à la main sur GitHub sans passer par les deux chemins de dépôt.
- **`app/issues.py::_parser_timeout`** (badge d'estimation, miroir documenté de `watcher.extraire_timeout`) applique la même règle, pour que le badge affiché à l'écran corresponde au budget réellement utilisé par le watcher.
- **Formulaire web** (`static/js/creation.js::timeoutDefautSelonMode`/`appliquerTimeoutDefaut`, appelées depuis `app.js::mettreAJourInfoProjet`) : la valeur pré-remplie du champ Timeout suit la même règle selon le mode choisi, recalculée au changement de projet ou de mode, jamais si le champ a déjà été modifié à la main ou synchronisé depuis un `TIMEOUT` collé (`detecterTimeoutDansCorps`).
- **`nouveau_projet.py::GABARIT_CONF`** : `TIMEOUT_CLAUDE` par défaut passé de 300 à 900 pour les **nouveaux** projets uniquement — aucun `configs/*.conf` existant n'est modifié.
- **Tests** : nouveau fichier `tests/test_plancher_timeout_ecriture_752.py` (11 scénarios : plancher écriture avec projet à 300s et à 1200s, lecture/lecture active inchangées, TIMEOUT présent jamais relevé, tâche Chef en écriture et en lecture, filet de sécurité `watcher.extraire_timeout` en écriture/lecture/TIMEOUT présent, gabarit `.conf` à 900). `tests/test_ordre_titre_entete_512.py` adapté au nouveau type de retour `(body, info_timeout)` de `construire_body`. `static/js/tests/creation.test.js` : 3 cas pour `timeoutDefautSelonMode`. Les 64 fichiers `tests/test_*.py` (`tests/lancer_tous_les_tests.py`) et les 291 tests JS (`node --test static/js/socle/tests/ static/js/tests/`) passent sans régression.
- **Documentation** : `ARCHITECTURE.md` — nouvelle section §12 « Plancher TIMEOUT pour les issues en écriture ». `BRIDGE_AGENT_DOC.md` — seule la phrase décrivant le TIMEOUT par défaut est modifiée (tableau des champs, §6 et §19).

**Rappel de déploiement** : après fusion, relancer le Watcher spool (`scripts/watcher_issues_inbox.py`), redémarrer `new_issue.py` (`app/issues.py` et `nouveau_projet.py` modifiés), relancer les watchers (`watcher.py` modifié) quand aucune issue n'écrit, puis Ctrl+Maj+R (JS modifié).
