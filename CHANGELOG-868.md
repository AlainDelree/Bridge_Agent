## 9 novembre 2026 — issue #868

Mise à jour automatique FACULTATIVE du dépôt de l'outil au lancement de `new_issue.py`, pour les installations locales sans service CCW (ex. poste Windows seul d'un ami, cf. #866/#867) — équivalent de `rafraichir_depot()` (#185) que le service CCW fait seul avant chaque cycle sur les machines d'Alain.

**Réglage facultatif, désactivé par défaut**, dans `identite_locale.conf` (racine du dépôt, gitignoré, #859) : `MAJ_AUTO_DEPOT = oui`, avec `MAJ_AUTO_DEPOT_REMOTE`/`MAJ_AUTO_DEPOT_BRANCHE` facultatifs pour suivre un remote/une branche différents de ceux déjà configurés dans le dépôt (utile si la copie elle-même a été personnalisée sur sa propre branche). Aucun changement de comportement pour les installations existantes d'Alain (ThinkPad, PC fixe) tant que rien n'est ajouté dans ce fichier — absent par construction sur ces deux machines.

**Réutilisation sans duplication** : `watcher.rafraichir_depot()` étendu (paramètres `remote`/`branche`/`timeout`/`exiger_propre`/`avec_liste_fichiers`, tous optionnels avec des défauts qui reproduisent EXACTEMENT le comportement et les lignes de log d'avant #868 pour l'appel historique de watcher.py) plutôt que dupliqué, et renvoie désormais un dict structuré (statut/message/fichiers) — ignoré par l'appel historique, exploité par le nouveau `watcher.tenter_maj_auto_demarrage()` qui lit les réglages ci-dessus et appelle `rafraichir_depot()` avec un délai court (8 s) et `exiger_propre=True` : contrairement au comportement par défaut (où `git pull --ff-only` refuse déjà seul tout écrasement), ce mode renonce ICI à la moindre tentative dès qu'une modification locale non enregistrée existe, même dans les cas où le pull resterait par ailleurs sans danger — une copie personnalisée par un tiers ne doit jamais être touchée. Une divergence d'historique (commit local non poussé) est ignorée proprement comme avant (fast-forward impossible).

**Rien n'est silencieux** : le résultat de chaque tentative (à jour, mis à jour avec la liste des fichiers changés, ignoré avec sa raison, échec avec sa raison) est affiché sur la sortie standard de `new_issue.py` (`_formater_message_maj_auto_depot`, capturée dans `logs/new_issue-session.log` sous l'installeur de session Windows, #864) et exposé dans l'interface elle-même via un nouveau bandeau (`app.config["MAJ_AUTO_DEPOT"]` posé avant `app.run()` → `app/vues.py::index()` → `templates/fragments/bandeaux.html`, classes CSS `.bandeau-eval-windows` déjà existantes de #741). Après une mise à jour réelle, ce même message rappelle explicitement que les watchers déjà démarrés tournent encore sur l'ancien code tant qu'ils ne sont pas relancés.

Nouvelle fonction publique `identite.valeur_locale()`, lecture générique d'une clé de `identite_locale.conf` (réutilisée par `tenter_maj_auto_demarrage` pour MAJ_AUTO_DEPOT/MAJ_AUTO_DEPOT_REMOTE/MAJ_AUTO_DEPOT_BRANCHE, sans dupliquer le lecteur `_lire_identite_locale` déjà interne à ce module, #859).

Tests (`tests/test_maj_auto_depot_868.py`, dépôts git réels temporaires, aucun accès réseau) : dépôt déjà à jour, mise à jour possible (fast-forward réel avec liste des fichiers), modifications locales non enregistrées (ignoré AVANT toute tentative de pull, fichier intact), historique divergé (ignoré, rien d'écrasé), délai dépassé sur le pull (échec explicite), réglage `MAJ_AUTO_DEPOT` absent (désactivé, aucune commande git), réglage actif avec remote/branche personnalisés (commande git construite vérifiée), et les messages affichés à l'utilisateur pour chaque statut. Suite complète de tests existante (`tests/test_*.py`, dont `test_auto_extinction_217.py` qui mocke déjà `rafraichir_depot`) rejouée sans régression.

Documentation : §8.1 (nouvelle sous-section) de `BRIDGE_AGENT_DOC.md` + paragraphe « Recevoir les mises à jour de l'outil » de `provisioning/windows/GUIDE_INSTALLATION_WINDOWS_SEUL.md` (§3), déjà présent dans le dépôt (issue #866/#865).
