## 10 novembre 2026 — issue #881

Essai réel sous Windows : deux issues GitHub identiques créées pour un seul fichier déposé dans `issues_inbox/` (même titre/contenu, même seconde de création, `logs/issues_inbox.log` montrant deux lignes `OK`).

**Cause établie par lecture du code (pas une hypothèse).** La liste des process montrait deux `scripts/watcher_issues_inbox.py` vivants — l'un descendant de la tâche planifiée `IssuesInbox` (`installer_demarrage_session.ps1`, démarrée `-DelaiDemarrageWatchersSec` après l'ouverture de session), l'autre ayant pour parent `new_issue.py` lui-même, relancé par sa propre tâche de session. `new_issue.py` démarre son propre watcher spool à chaque lancement **sauf** si `app.issues_inbox.watcher_inbox_actif()` le voit déjà actif — or cette fonction ne consulte QUE `logs/watcher-issues_inbox.pid`, qui n'était écrit QUE par `app.issues_inbox.demarrer_watcher_inbox()` (le lanceur), jamais par le script lui-même : un lancement direct par la tâche planifiée ne le renseignait donc jamais, rendant l'instance déjà active invisible à `new_issue.py`. Chaque instance a vu le fichier avant que l'autre n'ait terminé sa création ; l'anti-doublon (`gh issue list`) n'a pas pu voir à temps une création encore en cours ailleurs.

**Correctifs, tous dans `scripts/watcher_issues_inbox.py` :**
1. **Instance unique robuste au PID** (`acquerir_verrou_instance_unique`) : verrou système (flock POSIX non bloquant / verrouillage de plage Windows via `msvcrt`, détecté à l'import) posé dès le premier geste de `main()` et tenu sur le descripteur OUVERT pendant toute la durée de vie du process — libéré automatiquement par l'OS à la fin du process, propre ou brutale, quel que soit le futur PID réutilisé. Un second lancement journalise un message clair puis s'arrête (`sys.exit(0)`, jamais relancé par un superviseur qui ne redémarre que sur arrêt inattendu). `logs/watcher-issues_inbox.pid` est désormais aussi publié par ce script lui-même (seulement par le process qui a gagné le verrou) — même principe que `watcher.py` pour les watchers de projet — ce qui corrige la cause racine elle-même : `new_issue.py` ne relancera plus une instance déjà active, quel que soit son mode de lancement.
2. **Réclamation atomique** (`_reclamer_fichier`) : avant tout traitement, chaque fichier est déplacé de `issues_inbox/` vers `issues_inbox/en_cours/` sous son nom inchangé (jamais de suffixe visible dans les logs/notifications) — seule l'instance dont ce déplacement réussit poursuit ; belt-and-suspenders même si deux instances coexistaient malgré le verrou ci-dessus.
3. **Reprise après arrêt brutal** (`recuperer_fichiers_en_cours_orphelins`) : un fichier resté dans `en_cours/` dont le propriétaire (sidecar `.proprietaires/<nom>.pid`) n'est plus un process vivant est remis dans `issues_inbox/` au cycle suivant — jamais perdu, jamais retraité tant que le propriétaire est vivant.
4. **Anti-doublon complété** (`_creation_en_cours`/registre en mémoire) : couvre en plus deux fichiers DISTINCTS partageant le même titre, traités par la même instance avant qu'une requête `gh issue list` n'ait pu voir la première création — sans jamais remplacer l'anti-doublon GitHub existant, consulté en premier.

**Tests** (`tests/test_instance_unique_et_reclamation_881.py`) : verrou exclusif entre deux descripteurs puis libéré à la fermeture (vérifié aussi entre deux vrais process séparés, hors suite automatisée) ; réclamation refusée sur un nom déjà occupé ou déjà réclamé ; reprise d'un orphelin sans propriétaire vivant, fichier intact si le propriétaire est vivant, sidecar absent traité comme mort ; scénario explicitement demandé par l'issue — **deux traitements concurrents (threads) du même fichier déposé → une seule issue créée** ; anti-doublon en mémoire — deux fichiers distincts, même titre, traités concurremment → une seule création.

**Non vérifiable depuis l'environnement Linux de l'agent** : le chemin `msvcrt` (Windows) du verrou n'est pas exécutable ici — seul le chemin `fcntl` (Linux) a été vérifié, y compris entre deux vrais process séparés. **À essayer en vrai sur Windows** (voir `provisioning/windows/DEMARRAGE_SESSION_WINDOWS.md` §8, point 20) : déposer un fichier pendant que deux instances tournent volontairement et vérifier qu'une seule issue est créée.
