## 12 novembre 2026 — issue #886

Sur une installation Windows seule, le bouton « Interrompre » d'une issue a affiché à tort « Process encore vivant(s) après 5s : 27772 (C:\Python313\python.exe) — lock NON nettoyé » (suppression/revérification du verrou sautées) alors qu'une vérification manuelle immédiatement après (`Get-Process -Id 27772`) ne trouvait plus ce process.

**Cause établie par lecture du code** (`watcher.py`, `_pid_vivant`, branche `os.name == "nt"`, avant cette issue) : elle concluait « vivant » dès qu'`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` obtenait un handle — fait qui prouve seulement l'EXISTENCE de l'objet process dans le noyau Windows, pas qu'il exécute encore quoi que ce soit : un process déjà terminé reste ouvrable tant qu'un AUTRE handle le référence encore (son parent via `subprocess.Popen`, par exemple) — exact équivalent Windows du zombie Linux déjà corrigé en #748 (`os.kill(pid, 0)` réussit aussi pour un zombie). **Reste une SUPPOSITION, non tranchée par les données de l'incident** : qui tenait précisément ce handle superflu dans ce cas précis (parent, antivirus, fenêtre asynchrone de `TerminateProcess`/`TerminateJobObject`...).

**Correctif : `_etat_processus_windows` (watcher.py, nouveau)** — après `OpenProcess`, lit le code de sortie réel via `GetExitCodeProcess` ; un code différent de `STILL_ACTIVE` (259) est un FAIT CERTAIN de terminaison, indépendant du nombre de handles restants ⇒ `_pid_vivant` renvoie désormais `False` dans ce cas précis. Asymétrie prudente CONSERVÉE : si le code ne peut pas être lu (handle obtenu mais `GetExitCodeProcess` échoue), la réponse reste « vivant » comme avant cette issue — jamais de faux « mort ». **Branche Linux strictement inchangée.**

**Autres usages de `_pid_vivant` examinés** (acquisition des verrous `acquerir_verrou`/`taches_en_cours`/`nettoyer_verrous_perimes`, `app/watchers.py::watcher_actif` et `app/issues_inbox.py::watcher_inbox_actif` pour le panneau Infrastructure, `scripts/watcher_issues_inbox.py::_proprietaire_vivant` pour la reprise des fichiers orphelins, `watcher.py::_watcher_actif` pour la détection de conflit) : dans TOUS ces appels, `True` signifie « ne pas toucher » et `False` signifie « reprendre/libérer » — rendre `False` plus fidèle (moins de faux « vivant ») les rend tous plus corrects, sans scénario où une réponse « terminé » à la place de « vivant » serait dangereuse (un PID recyclé par l'OS continuerait de répondre `STILL_ACTIVE`, donc `vivant=True`, comme avant). Limite résiduelle documentée (inchangée, inhérente à l'API Windows) : un process dont le VRAI code de sortie vaudrait par coïncidence 259 resterait indiscernable d'un process actif — cas déjà couvert par l'asymétrie prudente existante, pas une régression de cette issue.

**`_attendre_signal_windows` (watcher.py, nouveau)** utilisé par `app/interruption.py::_arreter_arbre_windows` : remplace le `time.sleep(0.05)` fixe de la boucle d'attente par un `WaitForSingleObject` à droit `SYNCHRONIZE` — réveil dès que le noyau signale la terminaison réelle du process, plutôt qu'à la prochaine granularité de sondage. Le verdict reste tranché par `_etat_processus_windows`, pas par ce réveil (simple optimisation de latence).

**Message d'échec précisé** (`app/interruption.py::_arreter_arbre_windows`) : si l'attente de 5s se termine sans arbre confirmé mort, le message dit désormais explicitement si le code de sortie a été lu pour chaque survivant (« STILL_ACTIVE confirmé ») ou non (« code de sortie non lisible … — faux échec possible »), pour qu'un faux échec reste reconnaissable.

**Tests** : nouveau `tests/test_pid_vivant_windows_886.py` (substituts de `ctypes.windll`/`os.name`, comme les tests Windows existants — comportement non exécutable depuis cet environnement Linux) couvrant le cœur du correctif (code de sortie confirmant une terminaison réelle), la non-régression (`STILL_ACTIVE`, PID introuvable, lecture impossible → repli prudent), `_attendre_signal_windows`, et la non-régression stricte de la branche Linux (exécutée réellement, pas mockée). `tests/test_interruption_windows_701.py` mis à jour (les scénarios mockaient directement `_pid_vivant` ; ils mockent désormais `_etat_processus_windows`, le point d'appel réel depuis #886) + un nouveau scénario sur le message « faux échec possible ».

**BRIDGE_AGENT_DOC.md** : la seule mention existante (§16, « le bouton Interrompre … nettoie son verrou si le process est bien confirmé mort ») reste exacte après ce correctif — aucune mise à jour nécessaire.

**Non vérifiable depuis l'environnement Linux de l'agent** : le comportement réel sous Windows (l'API `ctypes.windll` n'existe pas ici). **À essayer par Alain** : sur un poste Windows, lancer une issue longue, cliquer sur « Interrompre », vérifier que la fenêtre annonce un succès et que le verrou est bien supprimé ; si un échec reproduit malgré tout, le nouveau message dira si le code de sortie a été lu ou non pour distinguer un vrai blocage d'un faux échec.

**Aucune issue de suivi créée sur GitHub** (consigne du projet) — pistes non traitées à garder en tête : élargir `_attendre_signal_windows` à un `WaitForMultipleObjects` si un arbre Windows compte un jour beaucoup de survivants simultanés (non fait ici : limite `MAXIMUM_WAIT_OBJECTS` à 64 handles, complexité jugée disproportionnée pour le cas réel, 1 à quelques process).
