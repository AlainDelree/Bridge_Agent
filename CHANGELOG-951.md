## 24 novembre 2026 — issue #951

Fermeture propre d'une issue EN COURS depuis sa ligne, avec avertissement quand l'issue est interactive (étude #939, suite #946/#947/#948/#949/#950). Avant cette issue, fermer une issue qui tournait encore obligeait l'ancien bouton « Interrompre et fermer » (retiré par #950) : il arrêtait TOUT le watcher du projet puis fermait avec un commentaire trompeur. Règle d'Alain : fermer une issue proprement SANS toucher aux autres issues du projet si c'est possible (cas normal) ; sinon (issue interactive, jamais couverte par l'interruption ciblée #949), ne le faire que si les autres issues du projet sont interrompues ou s'il n'y en a pas, avec un choix explicite.

Bouton « Fermer » désormais affiché aussi sur une issue EN COURS, à côté de « Interrompre » (`static/js/actions_ligne.js::boutonsActionLigne`, étendue : `timing.debut` posé → `['interrompre', 'fermer']` au lieu de `['interrompre']` seul — décision pure, testée sous Node). Toute la séquence est orchestrée CÔTÉ CLIENT par `static/js/app.js`, SANS nouvelle route (les trois routes existantes `/demander-interruption-issue` #949, `/issues-en-cours` #947 et `/fermer-issue` #950 suffisent) :

- **Cas normal** (`fermerIssueNormaleEnCoursDepuisLigne`) : confirmation (numéro, titre, effet — cette issue seule arrêtée puis fermée, les autres continuent, le travail déjà fait est conservé) ; dépôt de la demande d'interruption ciblée (#949) ; attente non bloquante (`await` sur `setTimeout`, jamais de boucle synchrone) que l'issue ne figure plus parmi les issues en cours (`GET /issues-en-cours`, sondage toutes les 3s, délai maximal 30s — `DELAI_MAX_ATTENTE_ARRET_FERMETURE_MS`) ; fermeture GitHub (`/fermer-issue`) SEULEMENT alors. Si la demande indique que l'issue a déjà fini entre-temps (`deposee:false`), fermeture immédiate. Si le délai est dépassé ou le dépôt échoue réellement (`succes:false`) : message clair, PAS de fermeture, l'issue reste dans son état, invite à réessayer.
- **Cas interactif** (`fermerIssueInteractiveDepuisLigne`) : interroge d'abord les AUTRES issues en cours du projet (`GET /issues-en-cours?exclure=<numero>`), enrichies de leur propre statut interactif relu localement (store du socle, `mecanismeInterruptionLigne` — aucun appel GitHub supplémentaire). Aucune autre issue en cours → confirmation simple puis arrêt du watcher entier (`/interrompre`, mécanisme historique #323) et fermeture. D'autres issues en cours, toutes non interactives → fenêtre à deux actions (réutilise l'overlay générique `#modal-confirmation`, déjà partagé par `static/js/creation.js`, aucun nouveau gabarit) : « Interrompre les autres puis fermer » (interrompt chacune via #949, attend leur arrêt avec le même délai, puis arrête le watcher et ferme) / « Annuler ». Au moins une autre issue ELLE-MÊME interactive → cette action n'est pas proposée (ne peut pas être interrompue proprement), la fenêtre l'indique et ne laisse que « Annuler ». Aucune issue n'est jamais arrêtée sans ce choix explicite.
- Garde anti-double-fermeture dédiée (`_fermeturesEnCours`, même patron que `_interruptionsEnCours` #748 mais ensemble DISTINCT) ; la ligne affiche « ⏳ Fermeture… » pendant l'attente.

Côté serveur (`app/issues.py::fermer_issue`) : retire désormais le label `needs-human` APRÈS avoir fermé l'issue (`gh issue edit --remove-label needs-human`, best-effort strict, isolé dans son propre `try/except` — un échec ne fait jamais échouer une fermeture par ailleurs réussie), jamais avant (une issue encore ouverte sans needs-human redeviendrait éligible au prochain cycle du watcher). Motif (point 4 de l'issue) : une issue CLOSED portant encore `needs-human` s'affichait comme un « échec » (badge ⚠️, `badgeLabel()`, détail/recherche) alors qu'elle a simplement été fermée depuis l'interface — cas courant depuis cette issue, puisque la séquence normale pose elle-même `needs-human` comme étape intermédiaire avant de fermer. Seul changement serveur de cette issue ; aucun appel GitHub supplémentaire hors la fermeture, son commentaire (inchangé) et ce retrait de label.
